# User Invites & Team Management — Design

**Date:** 2026-09-13
**Status:** Approved for planning

## Context

Today, invite/signup works via a single static secret: `process.env.INVITE_CODE`
on Railway, exposed to an ADMIN as a copy-paste link
(`GET /api/auth/invite-link` → `ManagerViewDialog.tsx`'s "Invite a teammate"
section). It's the same link for everyone, never expires, and isn't tied to
who it was meant for — anyone who obtains it (including after they've left)
can still create an account with it. New users already choose their own
password and only need to provide an email — that part already works exactly
as wanted.

There is no way to see who has an account, or to disable one. `functions/src/routes/users.js`
has list/update/delete endpoints, but nothing in the frontend calls them, and
there is no `isActive`/status concept anywhere in the schema — the only
existing lever is a permanent `DELETE`, unused.

The user asked for: a dedicated tab (not today's settings modal) to invite
people by email (a real, revocable, per-person invite) and to see/activate/
deactivate accounts.

## Decisions

| Question | Decision |
| --- | --- |
| Invite mechanism | Per-email, single-use, revocable, 7-day-expiring token — replacing the static `INVITE_CODE` entirely. Reuses the exact hashed-token pattern already proven by the forgot-password flow. |
| Where this lives | A new top-level "Team" tab, admin-only, alongside the existing "Settings" entry — not inside `ManagerViewDialog`. The modal's unrelated "Visible tabs" section is untouched; its "Invite a teammate" section is removed (superseded). |
| Deactivation enforcement | `authenticateToken` already re-fetches the user from the DB on every request — add one check there so deactivation takes effect on the deactivated user's very next request, not after their JWT eventually expires (JWTs are 30-day). |
| `SignupModal.tsx` | No changes. It already just passes an opaque `inviteCode` string through to `register()`; only what the backend does with that string changes (look up a per-invite record instead of comparing to a static env var). |

## Data model

**Important, corrects an assumption made earlier in this design process:**
this repo's production deploy does **not** run `prisma migrate deploy`.
`functions/start.sh` (the actual container entrypoint, per `railway.json`'s
`startCommand: "sh start.sh"` and the Dockerfile) runs `npx prisma generate`
then `npx prisma db push --accept-data-loss` on every boot — schema changes
take effect by editing `schema.prisma` directly; nothing in `prisma/migrations/`
is ever applied at runtime. The existing `migrations/` directories (e.g.
`20260907010000_add_scan_corrections`) exist only for local history/dev-database
use, generated by running `npx prisma migrate dev` against a local database —
they document intent but are not what makes a change live.

So: edit `functions/prisma/schema.prisma` directly (below), and optionally
also run `npx prisma migrate dev --create-only --name add_invites_and_user_active`
against a local dev database to keep a matching entry in `prisma/migrations/`
for consistency with existing practice — but the actual production schema
change happens via `db push` on the next Railway deploy, not from that file.

```prisma
model Invite {
  id          String    @id @default(cuid())
  email       String
  // SHA-256 of the raw token. Same reasoning as User.resetToken: the raw
  // token only ever exists in the emailed link, never in the database, so a
  // DB read alone can't produce a working invite link.
  tokenHash   String    @unique
  invitedById String
  invitedBy   User      @relation(fields: [invitedById], references: [id])
  expiresAt   DateTime
  usedAt      DateTime?
  revokedAt   DateTime?
  createdAt   DateTime  @default(now())

  @@index([email])
  @@map("invites")
}
```

Add to `model User` (`functions/prisma/schema.prisma`):

```prisma
isActive     Boolean  @default(true)
invitesSent  Invite[]
```

`isActive` defaults to `true` so every existing row is unaffected by the
migration — nobody currently signed in gets locked out.

## Backend (`functions/src/routes/auth.js`, `users.js`, `middleware/auth.js`)

### Enforcement: deactivated accounts lose access immediately

In `functions/src/middleware/auth.js`, `authenticateToken`'s existing
`prisma.user.findUnique` select (currently `id, username, email, role`) gains
`isActive`. Immediately after the existing `if (!user) { ... }` check, add:

```js
if (!user.isActive) {
  return res.status(403).json({ error: 'This account has been deactivated' });
}
```

In `auth.js`'s `POST /login`, after the existing password check succeeds,
before issuing the JWT:

```js
if (!user.isActive) {
  return res.status(403).json({ error: 'This account has been deactivated. Contact your administrator.' });
}
```

### Invite endpoints (new, in `auth.js`, near the existing `/invite-link` route)

`POST /api/auth/invites` — `authenticateToken`, `requireRole('ADMIN')`. Body:
`{ email }` (validated `isEmail().normalizeEmail()`). Generates a raw token
the same way `forgot-password` does (`crypto.randomBytes(32).toString('hex')`,
SHA-256-hashed for storage), creates an `Invite` row (`expiresAt` = now + 7
days, `invitedById` = `req.user.id`), and emails it via the existing
`sendEmail()`:

```js
const signupUrl = `${FRONTEND_URL}/#signup=${rawToken}`;
await sendEmail({
  to: [email],
  subject: "You're invited to Bexar CRE Acquisition CRM",
  text: `${req.user.username} has invited you to join the team.\n\n${signupUrl}\n\nThis link expires in 7 days and can only be used once.`,
});
```

If `sendEmail` throws, follow the same pattern as `forgot-password`: the
`Invite` row is already saved, log the error, but still return success to the
caller (the row exists; an admin can re-invite the same email later, which
just creates a new, separate `Invite` row — the old one simply expires unused).
Respond `{ success: true, invite: { id, email, expiresAt, createdAt } }`
(never the raw token, which already went out in the email).

`GET /api/auth/invites` — `authenticateToken`, `requireRole('ADMIN')`. Returns
all invites (`invitedBy` selected down to `{ username }`), newest first, with
a derived `status` per row computed server-side so the frontend doesn't
duplicate the logic:

```js
const status = invite.revokedAt ? 'revoked' : invite.usedAt ? 'used' : invite.expiresAt < new Date() ? 'expired' : 'pending';
```

Select/return: `id, email, status, invitedBy: { username }, createdAt, expiresAt, usedAt, revokedAt` — never `tokenHash`.

`DELETE /api/auth/invites/:id` — `authenticateToken`, `requireRole('ADMIN')`.
Sets `revokedAt: new Date()` (an `update`, not a hard delete — keeps the
row for the list's history). 404 via the existing `P2025` Prisma
not-found-error pattern if the id doesn't exist. No-op-but-success if already
revoked/used (nothing left to revoke, but nothing to error about either).

### Register — swap the static code for a real invite lookup

In `POST /api/auth/register`, replace the current block:

```js
// Verify invite code
if (!process.env.INVITE_CODE || inviteCode !== process.env.INVITE_CODE) {
  return res.status(403).json({ error: 'Invalid invite code' });
}
```

with:

```js
const tokenHash = crypto.createHash('sha256').update(inviteCode).digest('hex');
const invite = await prisma.invite.findUnique({ where: { tokenHash } });

if (!invite || invite.revokedAt || invite.usedAt || invite.expiresAt < new Date()) {
  return res.status(403).json({ error: 'This invite link is invalid, expired, or has already been used' });
}
```

After the user is successfully created (same `prisma.user.create(...)` call
already there, unchanged), stamp the invite as used:

```js
await prisma.invite.update({ where: { id: invite.id }, data: { usedAt: new Date() } });
```

`crypto` is already imported in `auth.js` (used by forgot-password). Delete
the now-dead `GET /api/auth/invite-link` route entirely — nothing calls it
once `ManagerViewDialog.tsx`'s invite section is removed (see Frontend). The
`INVITE_CODE` Railway env var becomes unused; leave it set (harmless) rather
than touching production config as part of this change — noting it as
removable in a future cleanup.

### Users — expose `isActive`, gate changing it

`GET /api/users` (`functions/src/routes/users.js`): add `isActive: true` to
the existing `select` (alongside `id, username, email, role, createdAt,
updatedAt`).

`PUT /api/users/:id`: add validation `body('isActive').optional().isBoolean()`
to the existing chain. Add an admin-gate for it, mirroring the existing role
check immediately below it:

```js
if (updates.isActive !== undefined && req.user.role !== 'ADMIN') {
  return res.status(403).json({ error: 'Only admins can change account status' });
}
if (updates.isActive === false && req.user.id === id) {
  return res.status(400).json({ error: 'Cannot deactivate your own account' });
}
```

(Mirrors the existing self-delete guard in the `DELETE` handler below it —
same reasoning: an admin should never be able to lock themselves out.) Add
`isActive: true` to the response `select` too.

## Frontend

### `src/lib/api.ts` — new functions, same fetch+`getAuthHeaders`+error pattern already used by `login`/`register`/`getInviteLink`

```ts
export interface TeamInvite {
  id: string;
  email: string;
  status: 'pending' | 'used' | 'expired' | 'revoked';
  invitedBy: { username: string };
  createdAt: string;
  expiresAt: string;
  usedAt: string | null;
  revokedAt: string | null;
}

export async function createInvite(email: string): Promise<{ success: true; invite: { id: string; email: string; expiresAt: string; createdAt: string } }> {
  const response = await fetch(`${API_BASE_URL}/api/auth/invites`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', ...getAuthHeaders() },
    body: JSON.stringify({ email }),
  });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || 'Failed to send invite');
  }
  return response.json();
}

export async function getInvites(): Promise<{ invites: TeamInvite[] }> {
  const response = await fetch(`${API_BASE_URL}/api/auth/invites`, { headers: getAuthHeaders() });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || 'Failed to load invites');
  }
  return response.json();
}

export async function revokeInvite(id: string): Promise<void> {
  const response = await fetch(`${API_BASE_URL}/api/auth/invites/${id}`, {
    method: 'DELETE',
    headers: getAuthHeaders(),
  });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || 'Failed to revoke invite');
  }
}

export interface TeamMember {
  id: string;
  username: string;
  email: string;
  role: 'ADMIN' | 'OPERATOR' | 'VIEWER';
  isActive: boolean;
  createdAt: string;
}

export async function getUsers(): Promise<{ users: TeamMember[] }> {
  const response = await fetch(`${API_BASE_URL}/api/users`, { headers: getAuthHeaders() });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || 'Failed to load team members');
  }
  return response.json();
}

export async function setUserActive(id: string, isActive: boolean): Promise<TeamMember> {
  const response = await fetch(`${API_BASE_URL}/api/users/${id}`, {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json', ...getAuthHeaders() },
    body: JSON.stringify({ isActive }),
  });
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new Error(error.error || 'Failed to update account status');
  }
  return response.json();
}
```

Remove `getInviteLink` (dead once its only caller, `ManagerViewDialog.tsx`,
no longer calls it).

### New tab: `src/components/team/TeamView.tsx`

Two sections, matching this codebase's existing card/section conventions
(e.g. `ContactsView.tsx`'s header + bordered-card layout):

1. **Invite by email** — an email `<Input>` + "Send Invite" `<Button>`
   calling `createInvite`, `toast()` on success/failure (matching the
   `toast` usage already in `ManagerViewDialog.tsx`), then refetches the
   invite list. Below it, a table of invites (`getInvites`) with columns
   Email / Status (a colored pill: pending=warn, used=success, expired=grey,
   revoked=danger, via the existing `pillClass` from `@/lib/pillBadge`) /
   Invited By / Sent / a "Revoke" button (only enabled when `status ===
   'pending'`, calls `revokeInvite` then refetches).
2. **Team members** — a table of `getUsers()` results: Name / Email / Role /
   Status (Active/Inactive pill, same `pillClass` convention already
   established for Contacts/Eviction/MLS) / Joined / an Active↔Inactive
   toggle button per row calling `setUserActive(id, !currentIsActive)`, then
   refetches. The toggle is disabled (with a tooltip/title, not hidden) for
   the signed-in admin's own row, matching the backend's self-deactivation
   guard — read `user.id` from `useAuth()` to compare.

## Out of scope

- Editing a user's role or deleting an account from the new Team tab (the
  backend already supports both via the existing `PUT`/`DELETE
  /api/users/:id`, but the user asked specifically for invite + monitor +
  activate/deactivate — role editing and deletion stay reachable only
  however they're reachable today, i.e. not from any UI yet either way).
- Removing the `INVITE_CODE` Railway env var (left in place, unused, to
  avoid touching production config as a side effect of this change).
- Resending an invite email for an existing pending invite (re-inviting the
  same address just creates a second, independent `Invite` row — acceptable
  for this pass; the old one simply sits unused until it expires).
